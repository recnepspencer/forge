# Worth Query Graph Authority Hardening Gate

> **Status:** Draft
>
> **Purpose:** refactor the `worth-topo`, `worth-spatial`, and
> `worth-kernel` production surfaces that became transitional after Forge
> Query Milestone 9.9, so Worth consumes Query graph touch obligation authority
> as a first-class runtime boundary before later boolean phases build on local
> ceremony.
>
> **Roadmap parent:** [worth_roadmap.md](./worth_roadmap.md),
> [milestone-7-roadmap.md](./milestone-7-roadmap.md)
>
> **Primary predecessors:** Forge Query Milestone 9.9, Worth Milestones 7.3
> and 7.4
>
> **Blocks:** broad 7.5+ boolean continuation work that would otherwise
> inherit local graph legality, handoff-only execution, or raw evidence scans
> as production posture.

## Goal

Make every Worth production path that participates in graph-shaped topology,
spatial boolean evidence, or construction birth consume Forge Query Graph Touch
Obligation Authority through Query-shipped proof/adoption surfaces, or else
emit explicit certified residue.

This gate is not a Forge Query feature milestone. Query 9.9 closed graph touch
obligation authority. This gate makes Worth stop carrying transitional
post-9.9 scaffolding around that authority.

By the end of this gate:

- `worth-topo` operator graph meaning lowers to Query touch descriptors,
  registrations, selector coverage, support posture, and execution proof
  without rebuilding local obligation selection
- `worth-spatial` remains spatial and geometric evidence authority without
  impersonating Query graph authority
- `worth-kernel` primitive construction birth consumes Query graph obligation
  execution proof instead of handoff-only or broad-selector substitutes
- 7.3 split and 7.4 loop ledgers remain exclusive downstream boolean products
  after the refactor
- certified residue is reduced where possible and named where not possible
- public facades expose adoption/proof receipts while keeping proof internals
  unforgeable

## Why This Gate Exists

Worth recently finished heavy boolean-prep work in the 7.3 edge-splitting and
7.4 loop-reconstruction specs. Those specs deliberately built receipt-backed,
proof-bearing artifact ladders so later boolean phases do not reopen raw event,
split, continuation, or loop truth.

Forge Query 9.9 changed the lower foundation beneath those ladders: graph touch
meaning can now be selected, dispatched, executed, evidenced, and adopted
through Query-owned Graph Touch Obligation Authority. That means any remaining
Worth production code that keeps local graph legality, local support pinning,
local proof-obligation tables, handoff-only execution claims, raw evidence-row
scans, or string-linked stage checks is no longer just cleanup debt. It is a
competing authority risk.

This gate reconciles Worth with the new Query authority before later boolean
milestones amplify the problem.

## Adversarial Constraint

Given any Worth production path that participates in the 7.3/7.4 planar
boolean chain, topology operator graph mutation, spatial graph-affecting
evidence, or primitive construction birth, graph-touch legality must either be
selected, planned, executed, and evidenced through Forge Query Graph Touch
Obligation Authority, or be denied/certified as explicit owner-tagged residue.

No `worth-topo` operator catalog, `worth-spatial` evidence surface, or
`worth-kernel` construction path may satisfy closeout by rebuilding local graph
selectors, local invariant packs, handoff-only execution claims, raw
evidence-row scans, string-prefix stage linkage, or support-pinning ceremony
that competes with Query's Consumer Kit.

If later boolean phases can consume a Worth-local graph legality artifact
instead of a Query graph obligation proof, a split/loop ledger receipt, or
explicit residue, this gate has failed.

## Product Decision Lock

- Query owns graph touch descriptors, operating worlds, obligation
  registration, selection, dispatch, support posture, execution proof,
  Consumer Kit adoption, and graph-obligation residue manifests.
- `worth-topo` owns topology operator semantics and topology truth. It may
  declare which topology operator touches which relation, but it may not own a
  second obligation selector.
- `worth-spatial` owns geometry and spatial evidence. It may provide witness,
  split, loop, tolerance, and replay evidence, but it may not promote spatial
  evidence into Query graph authority.
- `worth-kernel` owns construction orchestration and workload composition. It
  must consume Query-lowered topology/spatial contracts through proof-bearing
  receipts; it may not claim graph execution from prepared handoff alone.
- 7.3 split ledgers and 7.4 loop ledgers remain the exclusive downstream
  boolean truth artifacts for their phases.
- Remaining residue must be explicit, capped, owner-tagged, introduced in a
  named phase, and tied to a removal trigger.
- No new public constructor may let consumers forge graph obligation proof,
  support pins, execution receipts, adoption manifests, or residue rows.

## Exclusivity Law

After this gate, Worth production code may consume Query graph obligation
authority through Query-shipped proof/adoption surfaces, or it may expose
explicit certified residue. It may not carry a second local graph obligation
authority.

## Deletion Target Classes

This gate is expected to delete whole classes of transitional support code, not
only rename or relocate it. A phase is incomplete if it preserves a support
surface whose only remaining job is to restate proof already carried by the
canonical Query graph authority receipt, the split ledger receipt, the loop
ledger receipt, or an explicit residue manifest.

The implementation must actively hunt these deletion classes:

- duplicate support reports that summarize Query support posture without being
  the canonical support proof consumed by an executed graph obligation receipt
- local support-pin wrappers that can be derived from Query Consumer Kit
  support pins or graph obligation support matrix rows
- graph-obligation adoption facades that prove only API availability rather
  than selection, execution, support posture, and residue
- local ceremony audits that exist only to compensate for missing typed
  residue rows or deleted local guard classes
- blueprint proof-obligation rows that duplicate Query graph obligation
  registrations or selector coverage
- handoff-only result helpers that survive only because executed compose proof
  is not yet threaded through the ordinary receipt
- raw evidence-row scan helpers and copied evidence-row vectors that should be
  replaced by typed evidence-stage index products
- string-prefix stage-link helpers that should be replaced by typed receipt
  identity and stage-index linkage
- compatibility reports whose rows are now derivable from one canonical
  adoption/proof receipt
- certification-only fixtures that accidentally preserve production-looking
  local authority entrypoints

Every item in these classes must end the gate in exactly one state:

- deleted
- collapsed into a canonical Query / ledger / receipt proof surface
- moved behind an explicitly certification-only fixture boundary
- retained as capped, owner-tagged residue with a removal trigger
- blocked by a named Query capability gap that prevents deletion

No item may survive because it is "useful context" or "extra safety." Extra
proof is useful only when it proves a distinct authority boundary. Otherwise it
is duplicate authority and should be removed.

## Arch Law 41 Discovery Strategy

Arch Law 41 says a type must encode what has been proven about a value, not
merely what the value contains. This gate uses that law as a discovery tool.
The implementation should make weaker values stop compiling wherever stronger
authority is required.

The discovery strategy is:

1. identify local values that currently look like proof because they contain
   the right fields, strings, counters, or digests
2. introduce proof-bearing types for the actual authority phase
3. change production APIs to require the strongest honest proof type
4. let the compiler reveal every caller still passing lower-authority reports,
   raw rows, copied digests, handoffs, fixtures, or support summaries
5. replace each failing caller with canonical Query proof, ledger receipt
   proof, certification-only test support, explicit residue, or a named Query
   capability gap

The gate should prefer proof-bearing type transitions such as:

```rust
RawWorthGraphAuthoritySurface
AuditedWorthGraphAuthoritySurface
QueryAdmittedGraphAuthority
GraphObligationSelectedAuthority
GraphObligationExecutedAuthority
ReceiptBackedGraphAuthority
```

and domain-specific witnesses such as:

```rust
TopologyOperatorGraphAuthorityWitness
SpatialEvidenceAuthorityWitness
EvidenceStageIndexWitness
PrimitiveBirthGraphAuthorityWitness
ExecutedPrimitiveBirthGraphAuthority
```

Do not let these collapse into aliases around `String`, untagged digests, or
plain reports. Same-shaped values with different authority must be different
types. A report that describes support posture is not a witness that support
was consumed by an executed graph obligation. A handoff that was admitted is
not an executed construction birth. A split ledger digest is not a loop ledger
digest. A test fixture that contains plausible rows is not production proof.

The implementation must add compile-fail guards for lower-authority promotion
attempts, including:

- support report is not graph authority
- crate-level Query adoption is not graph obligation proof
- admitted handoff is not executed birth
- raw evidence rows are not an evidence-stage index
- string-prefix stage links are not typed receipt linkage
- split ledger digest is not loop ledger digest
- synthetic graph authority fixture is not production proof
- residue row literal is not a certified residue manifest

## Phase Plan

This gate is ordered for an automation loop that can clean one bounded owner
surface until it is done, run QA, and only then move on. The order is therefore
not a taxonomy of authority concepts. It is the implementation order:
discover globally, pin the Query contract, clean `worth-topo`, clean
`worth-spatial`, clean `worth-kernel`, then prove the boolean chain and
cross-crate closeout.

Each crate cleanup phase owns its local facade and compile-fail lockdown. Public
proof fences must not be deferred to a final global facade phase; otherwise
agents will keep using internal constructors and lower-authority fixtures as
temporary conveniences that become hard to remove.

A phase is complete only when its deletion ledger rows are resolved, its public
surface is locked, its compile-fail contracts prove weaker authority cannot be
promoted, and its focused QA suite passes.

### Phase 1: Global Discovery And Gate Harness

Freeze the full Worth graph-authority surface map before crate cleanup starts.
Search may seed the candidate root list, but the authoritative discovery move
is compiler-led: deliberately demote, seal, privatize, rename, or witness-gate
the root structs, constructors, exports, and trait implementations that let
local graph authority, support reports, proof wrappers, handoff-only execution,
raw evidence scans, string-prefix stage linkage, or support-pinning ceremony
act like production authority.

The output of this phase is a production inventory and deletion ledger that the
automation script can use as a scoreboard. Every audited source row must name:

- owner crate and subsystem
- authority class
- deletion target class, if any
- discovery source: `compiler`, `compile-fail`, `public-facade`,
  `certification-only`, or `search-seed`
- action: `keep`, `collapse`, `delete`, `residue`, or `query-gap`
- replacement surface or blocker
- QA evidence that prevents silent drift

**Relevant subsystems**

- `worth-topo` topology operator adoption and query-native boundary
- `worth-spatial` query adoption and workload evidence ledger
- `worth-kernel` construction query authority and graph obligation adoption
- Forge Query Consumer Kit and Graph Touch Obligation Authority

**Warnings**

- Do not classify by filename alone. A file named `query_adoption` may be
  honest posture reporting, graph-obligation proof, certification-only support,
  or residue.
- Do not hide production debt inside test/certification language. A production
  path used by workload or boolean execution remains production even if tests
  are the only current caller.
- Do not demote every root at once if the compiler output becomes unreadable.
  Break one authority family at a time and record the downstream consumer set
  before moving to the next family.
- Do not commit intentionally broken discovery edits. Commit enforced APIs,
  inventory rows, deletion rows, and compile-fail guards.

**Test requirements**

- Adversarial compiler-discovery test: each root authority family has a
  discovery record showing the intentional break, the downstream compile
  failures it exposed, and the final enforced API that replaced the break.
- Adversarial coverage test: every audited Worth production source is
  represented in a typed inventory row.
- Adversarial leakage test: adding an unclassified source under the audited
  paths fails certification rather than silently becoming implicit residue.
- Adversarial deletion test: duplicate support reports, local support-pin
  wrappers, raw evidence scan helpers, handoff-only result helpers, and
  blueprint proof-obligation rows cannot be classified as `keep` unless they
  prove a distinct authority boundary not carried by Query or ledger receipts.
- Adversarial proof-phase test: every production API discovered in this phase
  accepts the strongest phase-typed authority object it semantically requires.

**Engineering decisions**

- The inventory and deletion ledger are code artifacts, not spreadsheet prose.
- The matrix records what the compiler taught us; it is not the discovery
  mechanism.
- Prefer proof-bearing wrappers and witness tokens over runtime checks.
- Keep provenance in docs and reports, but do not name production modules after
  milestones unless the responsibility is historical compatibility itself.

### Phase 2: Forge Query Contract Baseline

Pin the exact Query surfaces Worth is allowed to consume before rewriting crate
internals. This phase defines the canonical Consumer Kit, graph obligation,
selector, support posture, execution, receipt, residue, and public facade
contracts that later phases must use.

This is a short baseline phase, but it is load-bearing. Without it, each Worth
crate can accidentally define its own local meaning of Query proof.

**Relevant subsystems**

- `forge-query::facade::consumer_kit::*`
- Forge Query graph touch descriptors, selectors, obligation registrations,
  support posture, execution rows, receipts, adoption manifests, and residue
  manifests
- Query docs for Graph Touch Obligation Authority and Consumer Kit adoption

**Warnings**

- Do not treat crate-level Query adoption as graph obligation execution proof.
- Do not accept local required-family lists, local support pinning, or fabricated
  receipts when the Consumer Kit owns the proof surface.
- Do not extend Worth locally when the blocker is really a Query selector,
  support, receipt, or Consumer Kit API gap.

**Test requirements**

- Adversarial contract test: Worth can name the Query types that represent
  adoption posture, selector coverage, support pinning, selected obligation,
  executed obligation, receipt, and residue without local substitutes.
- Adversarial weaker-proof test: crate-level adoption status cannot satisfy an
  API requiring graph obligation execution proof.
- Adversarial Query-gap test: any missing Query capability is represented as a
  named blocking row, not a Worth-local workaround.

**Engineering decisions**

- Prefer updating Query specs or Query APIs when exact authority cannot be
  expressed honestly.
- Worth phases may define domain-specific witnesses only when they wrap or
  consume canonical Query proof instead of competing with it.

**Required work**

- Make query-native boundary progression phase-typed: raw handoff, admitted

- Delete blueprint-local graph legality where Query now owns the covered lane,

**Warnings**

**Test requirements**

- Adversarial phase-promotion compile-fail test: raw handoff cannot be passed

- Adversarial facade test: public consumers can obtain topology adoption and

### Phase 8: Cross-Crate Closeout Certification

Close the gate with one cross-crate certification story. The closeout must prove
that Worth consumes Query graph authority honestly, that 7.3/7.4 boolean ledger
exclusivity survived the cleanup, and that any remaining residue is explicit,
capped, owner-tagged, and non-competing.

The closeout must also prove the deletion ledger closed: every targeted support
report, local proof wrapper, handoff-only helper, raw evidence scan helper,
string-prefix stage link, blueprint proof-obligation row, and compatibility
report is deleted, collapsed, certification-only, residue, or Query-gap.

**Relevant subsystems**

- `worth-topo`
- `worth-spatial`
- `worth-kernel`
- Forge Query Consumer Kit
- Worth roadmap and test-requirements docs

**Warnings**

- Do not close on API presence. Close on proof that the production chain uses
  the APIs.
- Do not close on a single happy-path boolean or primitive construction case.
- Do not delete residue rows without a test that proves the former bypass is
  impossible.
- Do not add a closeout doc before the certification suite exists.

**Test requirements**

- Adversarial closeout matrix: every audited source from Phase 1 is covered,
  deleted, blocked as Query-gap, or represented as capped residue.
- Adversarial reference-consumer test: topo, spatial, and kernel public facades

- Adversarial anti-theatre test: synthetic Query proof, local support pins,

  string-prefix stage links cannot satisfy the closeout suite.
