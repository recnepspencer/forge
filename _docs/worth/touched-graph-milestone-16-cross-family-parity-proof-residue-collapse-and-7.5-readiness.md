# Milestone 16: Cross-Family Parity Proof, Residue Collapse, And 7.5 Readiness

## Goal

Close the touched graph roadmap only when the remaining ordinary families prove
they are instances of one semantic-graph architecture, the surviving residue is
mechanically exact, and `Milestone 7.5` can inherit touched authority without
reopening local routing, overlap, replay, cache, or diagnostic folklore.

## Semantic Definitions

Milestone 16 is only honest if the closeout vocabulary below has one fixed
meaning.

- **Cross-family parity proof**: a typed certification claim that multiple
  family kinds consume the same upstream semantic-graph authority chain without
  inventing family-local routing meaning after declaration.
- **Family kind**: one of the roadmap-owned ordinary family classes:
  read-routing, validator/invariant routing, invalidation, evidence lookup,
  replay/undo, conflict-independence-batch admission, compiled-product
  equivalence or reuse, public proof, and derived diagnostics. Milestone 16 is
  required to certify every listed family kind explicitly; grouped proof for
  "most of them" is not acceptable closeout.
- **Architecture-alignment row**: one mechanically derived row describing how a
  live ordinary surface maps onto the unified semantic-graph architecture. A
  row is evidence, not prose.
- **Residue collapse**: the mandatory reduction of any remaining ordinary-path
  second ontology into one of four states only:
  - deleted
  - capped non-ordinary residue
  - concrete Query-gap
  - explicit later-scope blocker outside this roadmap
- **Representative parity path**: a real end-to-end ordinary path whose proof
  chain demonstrates that one touched graph language drives multiple family
  kinds without route rediscovery.
- **7.5 readiness input**: the typed handoff artifact showing that overlap
  extraction and downstream graph-read work can start from touched authority,
  family declarations, selected route identity, and public proof handoff
  products rather than local helper languages.
- **Second ontology**: any family-local language for routing, sameness,
  overlap, public explanation, or Query posture that is not derived from the
  shared touched graph, aspect, compiled-product, or planner-owned routing
  contracts.
- **Query-gap**: a concrete upstream capability blocker in `forge-query`, not a
  vague future-work bucket. If the missing capability cannot be named precisely,
  the issue is not a Query-gap.

## Why This Milestone Exists

Milestones 13 through 15 can still succeed locally while the kernel fails
globally.

That failure mode looks like this:

- conflict and batch admission are aspect-routed
- reuse is contract-driven
- planner-owned routing and public proof exist
- diagnostics are receipt-backed
- but each family still carries a slightly different idea of what the system is

If that happens, Worth does not yet have a semantic-graph kernel. It has a
collection of better local systems that happen to touch the same data.

Milestone 16 exists to close that architectural escape hatch. This milestone is
not documentation polish, residue gardening, or a celebratory closeout. It is
the proof that touched graph authority, aspects, compiled-product identity, and
planner-owned routing really did converge into one declarative kernel.

## Governing Summaries

- `MENTALITY.md`: protect the real hard problem first. The hard problem here is
  not "wrap up the roadmap"; it is "prove the covered families are actually one
  architecture and refuse cosmetic closeout."
- `arch_laws.md`: protect proof-bearing phase transitions, authority versus
  derivation separation, explicit equivalence contracts, lowered execution, and
  facade-only exposure. Milestone 16 must certify those laws across family
  kinds rather than inside one lane at a time.
- `composition_laws.md`: protect responsibility-named decomposition. Cross-
  family parity, residue collapse, readiness handoff, and reintroduction
  denials may not collapse into one mega closeout file or one report builder.
- `domain_structure_laws.md`: protect directory truth. The tree must visibly
  distinguish shared parity contracts, family contributors, residue collapse,
  readiness handoff, and firewall proof instead of hiding them inside generic
  closeout folders.
- `perf_laws.md`: protect semantic-delta-bounded execution and forbid repeated
  rediscovery. The final architecture must still route from carried proof,
  selected identity, and explicit Query posture rather than broad scans or
  helper reconstruction.
- `touched-graph-roadmap.md`: protect milestone order. Milestone 16 belongs
  after planner-owned routing because parity is only honest once public proof
  and diagnostics consume the same route authority execution already consumed.

## Adversarial Constraint

Worth must survive a long mixed ordinary workflow where one small locality
change flows through:

- query-backed read routing
- validator and invariant routing
- invalidation
- evidence lookup
- replay and undo scope
- conflict, independence, and batch admission
- compiled-product equivalence and reuse
- planner-owned public proof
- derived diagnostics

while later consumers such as `Milestone 7.5` are allowed to observe only the
typed authority and handoff products already emitted by the kernel.

If any covered ordinary path still needs to reopen topology internals,
recompute overlap, rediscover replay scope, restate Query support posture,
rebuild reuse meaning, or hand-author public explanation from local rows or
helpers, the milestone has failed.

## Product Decision Lock

- Milestone 16 is a parallel-cutover milestone. Any final parity, residue, or
  readiness responsibility that does not already live in a responsibility-named
  lane must be created beside the displaced closeout/helper lane before caller
  cutover begins.
- This milestone is forbidden from performing an in-place "final cleanup" of
  mixed closeout folders and then calling that architectural certification.
- A phase may claim cutover progress only when all of the following are true
  for that phase's responsibility:
  1. the new responsibility-named folder lane exists on disk
  2. the new lane owns the production types that express that responsibility
  3. at least one ordinary caller imports the new lane directly
  4. the displaced lane is no longer the write location for new ordinary-path
     architecture logic
- Once the new lane exists, later ordinary-path edits for that responsibility
  must land there. Edits in the displaced lane are allowed only for import
  cutover, deletion, explicit residue capping, or firewall proof.
- The required lifecycle shape is:
  `coverage_inventory -> parity_contract -> representative_path ->
  family_contributor_proof -> readiness_handoff -> source_firewall ->
  residue_collapse -> closeout`.
- `worth-schema` owns the shared parity and readiness contract vocabulary.
- `worth-kernel` owns cross-family parity orchestration, live coverage ledger
  derivation, representative path proof, residue collapse, readiness handoff,
  and reintroduction firewalls.
- `worth-topo` owns topology read, validator or invariant, and invalidation
  parity contributors where topology remains the authoritative family source.
- `worth-spatial` owns evidence lookup and spatial retained-surface parity
  contributors where spatial remains the authoritative family source.
- `forge-query` remains the owner of Query support posture, support-matrix
  truth, boundary-envelope truth, and consumer-residue proof. Milestone 16 must
  consume those surfaces exactly as provided. It must not invent a Worth-local
  "Query gap ledger" language.
- The only valid reasons to touch `forge-query` during this milestone are
  concrete missing capabilities that can be named precisely. Absent that, Worth
  must fix itself and continue.
- Target directory skeleton:

```text
crates/worth-schema/src/data/authority/touched_graph_parity_closeout/
  mod.rs
  family_kind.rs
  architecture_claim.rs
  coverage_row.rs
  residue_classification.rs
  readiness_input.rs

crates/worth-kernel/src/workload_composition/touched_graph_parity_closeout/
  mod.rs
  coverage_inventory/
  representative_path/
  family_contributors/
  readiness_handoff/
  residue_collapse/
  source_firewall/

crates/worth-topo/src/projection/touched_graph_parity_closeout/
  mod.rs
  read_family/
  validator_invariant_family/
  invalidation_family/

crates/worth-spatial/src/workload_platform/touched_graph_parity_closeout/
  mod.rs
  evidence_lookup_family/
  retained_surface_family/
```

- These lanes are certification and closeout consumers of the Milestone 13-15
  architecture. They must not become alternate ordinary routing owners.
- The default displaced or replacement-path inventory for this milestone must
  name exact paths, not categories. Phase 1 starts from:
  - `crates/worth-kernel/src/workload_composition/planner_owned_routing_inventory/`
  - `crates/worth-kernel/src/workload_composition/touched_graph_parity_closeout/coverage_inventory/`
  - `crates/worth-kernel/src/workload_composition/touched_graph_parity_closeout/family_contributors/`
  - `crates/worth-topo/src/projection/touched_graph_parity_closeout/read_family/`
  - `crates/worth-topo/src/projection/touched_graph_parity_closeout/validator_invariant_family/`
  - `crates/worth-topo/src/projection/touched_graph_parity_closeout/invalidation_family/`
  - `crates/worth-spatial/src/workload_platform/touched_graph_parity_closeout/evidence_lookup_family/`
- The spec intentionally treats "remaining mixed helper" as a failed inventory
  state. Once Phase 1 live coverage exists, every displaced or future lane must
  be named by its exact module or folder path in that ledger.

### Phase 1: Cross-Family Coverage Inventory Cut Line

Freeze the live ordinary surfaces that still claim touched-graph architecture
meaning before any parity proof or residue collapse begins.

**Relevant subsystems**

- `worth-spatial` workload-platform routing contributors
- `forge-query` support and residue evidence surfaces

**Relevant APIs**

- `WorthTouchedGraphConflictArchitectureAlignmentReport`
- `query_consumer_residue_audit(...)`
- `project_workspace_support_snapshot(...)`

**Warnings**
- Do not treat the Milestone 15 residue ledger as a sufficient Milestone 16
  coverage matrix.
- Do not hide multiple family kinds under one broad "public closeout" row.
- Do not count certification-only helpers as ordinary architecture proof.
- Do not prove ordinary-path reachability from facade re-exports, parity-closeout
  wrappers, or public-closeout proxies when a lower live route caller exists.

**Test requirements**
- `cross_family_coverage_inventory_is_scope_complete`: fails if any covered
  ordinary family kind lacks a live coverage row naming owner, source path,
  authority chain, and residue posture.
- `cross_family_coverage_inventory_rejects_hidden_second_ontologies`: fails if
  a live ordinary surface still teaches routing, overlap, reuse, or Query
  posture semantics that are not named in the inventory.

**Engineering decisions**
- Coverage rows must name `family_kind`, `current_surface`,
  `upstream_authority_source`, `selected_route_or_equivalence_source`,
  `public_or_internal_consumer_kind`, and `residue_posture`.
- Coverage rows must also name:
  - `source_path`
  - `current_owner_crate`
  - `replacement_lane`
  - `selected_identity_fields_consumed`
  - `query_surface_kind` with values `not_query`, `support_posture`,
    `consumer_residue`, or `boundary_envelope`
  - `ordinary_path_reachable` as a yes/no certification field
- The coverage inventory must be mechanically derived from live production
  surfaces, not maintained as a prose checklist.
- If a family's ordinary authority is consumed through another live route lane,
  the row must name that exact caller path and current surface rather than a
  family-local helper packet.
- Every later phase consumes these rows; no later phase may redefine family
  coverage ad hoc.
- The coverage inventory must contain at least one ordinary-path row for every
  family kind named in `Family kind`. A family kind with zero rows is an
  explicit closeout failure, not an implied "not applicable."
- If one family kind has multiple ordinary subfamilies, the inventory must
  expose multiple rows rather than collapsing them into one summary row.
- At minimum, the phase-1 inventory must name separate live ordinary rows for:
  replay and undo when they remain distinct, conflict vs independence vs
  batch-admission when those lanes remain distinct, and compiled-product
  equivalence vs reuse when those lanes remain distinct.
