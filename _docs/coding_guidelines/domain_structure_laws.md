# Domain Structure Laws

1. A codebase is not organized by placing files into folders; it is organized when its physical structure preserves the distinctions the system must reason about. Meaning, authority, lifecycle, truth source, failure mode, dependency direction, ownership, volatility, scale, and boundary crossing are structural facts, not filing preferences. Filesystem objects are only the encoding. The real object is the responsibility boundary. If the tree does not teach the system, it is not architecture; it is storage.

2. A structural boundary is required wherever collapsing two concepts would destroy semantic separability. A concept is structurally separable when it can be understood, tested, owned, replaced, deleted, versioned, scaled, or depended on without dragging unrelated concepts with it. Relatedness is not cohesion. Everything inside a domain is related; cohesion requires shared structural fate. A folder that groups things because they are “kind of about the same area” is not a boundary — it is postponed classification, and postponed classification becomes silent coupling.

3. Every folder must earn its boundary. A folder earns its existence only when it preserves a distinction the system must reason about: meaning, lifecycle, authority, truth source, failure mode, test strategy, dependency direction, scale, ownership, or replacement boundary. A folder that exists only because “these files are related” has not earned its boundary. Unjustified folders create false maps; unjustified consolidation creates structural sinkholes.

4. A domain is a recursive responsibility space, not a top-level label. “Organize by domain” is only the first cut. A domain may contain subdomains, subsystems, invariant families, operation families, lifecycle phases, strategies, projections, adapters, authority regimes, and state categories. The rule continues recursively until further decomposition no longer preserves a meaningful distinction. A domain that does not decompose internally eventually becomes a horizontal layer wearing a vertical name.

5. The tree must let the reader predict where the system can change, fail, recover, scale, be tested, be owned, or be replaced. A flat tree is not simpler when it hides independent responsibilities; it transfers structure from directories into oversized files, overloaded names, reader memory, and refactor traps. Hidden fracture lines do not disappear; they reappear as god files, unstable names, accidental coupling, and changes that become dangerous because no boundary tells the reader where they stop.

6. A structural name must let the reader predict its contents. A valid folder, file, module, type, or function name tells the reader what belongs inside, what does not belong inside, and why the construct exists. Names like `common`, `helpers`, `logic`, `manager`, `processor`, `data`, and `utils` fail because they predict almost nothing and reject almost nothing. A name that cannot guide the next edit is not a boundary; it is a bucket, and buckets become structural sinkholes.

7. Name length optimizes for correct classification, not brevity. Short names are good only when they preserve meaning. A longer name that teaches the domain on first read is cheaper than a short name that requires context, tribal knowledge, or opening the file. The cost to minimize is not character count; it is misclassification. Obscure brevity is not elegance — it is hidden coupling that forces every reader to reverse-engineer intent.

8. Provenance is not structure. Names based on milestones, tickets, prompts, sprints, temporary phases, implementation sequence, or “new” work describe how code arrived, not what it owns. `milestone_3_tests`, `phase_2_logic`, `ticket_483_fix`, and `new_validation` are provenance names, not structural names. Provenance belongs in commits, changelogs, issue trackers, release notes, migration metadata, and audit trails. It belongs in the tree only when historical compatibility is itself the responsibility. Provenance names create semantic drift because the milestone remains after the responsibility changes.

9. Names must be clear at their visibility radius. Private files may rely on folder context; public exports must carry enough semantic meaning to stand alone. Repeating every ancestor in every filename creates noise, but omitting necessary context from a public type exports ambiguity. Internal structure should be locally readable; public surfaces must be globally intelligible. A name that is clear only inside one author’s memory is not clear at its visibility radius.

10. Missing hierarchy reappears as overloaded names. When filenames need repeated prefixes, suffixes, numbers, `advanced`, `new`, `shared`, `common`, `helpers`, or category labels to remain distinguishable, the tree has failed to encode a real structural axis. Correct hierarchy removes name pressure by giving each axis of meaning its own place. When hierarchy is missing, filenames become miniature directory trees with no enforceable boundaries.

11. Each structural level must encode one dominant axis of classification. A level may classify by domain concept, lifecycle phase, authority regime, state category, operation family, boundary type, or strategy. Mixing axes at the same level creates folders that cannot extend coherently and names that must carry too much meaning manually. Axis mixing is structural debt because the next file has no principled place to go.

12. Category labels are valid only when they name shared structural fate. `validation`, `operations`, `workflows`, `algorithms`, `actions`, `services`, and `invariants` are not automatically wrong, but they are suspicious because they often describe activity rather than responsibility. A category is a filing cabinet. A responsibility is a reason to exist. If the contents do not change together, fail together, test together, and get debugged through the same mental model, the category has not earned its folder. Filing cabinets become junk drawers when they cannot reject future code.

13. Stable concepts must own volatile mechanisms. Domain responsibilities, authority boundaries, and source-truth definitions must shape the tree before frameworks, protocols, libraries, storage engines, generated artifacts, transport formats, and vendor integrations do. A stable responsibility nested under `react`, `postgres`, `grpc`, `redis`, or a vendor name inherits the tool’s lifecycle and will be renamed for the wrong reason. That is tool-shaped architecture: implementation volatility disguised as domain change.

14. Layers are authority questions, not folder templates. Boundary, core, storage, integration, diagnostics, and presentation are not mandatory directories; they ask who owns translation, policy, persistence, orchestration, explanation, and display. Create structure that preserves those authority distinctions, not folders that satisfy a pattern. A layer name is useful only when it clarifies who may decide, who may translate, who may persist, and who may observe. Template-shaped layers without authority distinctions create ceremonial structure and hide the real domain topology.

15. Source truth and projections must have asymmetric structure. Canonical definitions, authority records, and domain contracts are upstream of generated code, caches, indexes, SDKs, read models, diagnostics, and materialized views. The tree must make it obvious which artifacts may be edited, which artifacts are derived, and which artifacts can be destroyed and rebuilt. If a projection looks like source truth, ownership has inverted.

16. Authoritative state, derived state, cached state, speculative state, external observations, and diagnostic artifacts must not share structural space. These objects have different meanings, lifecycles, invalidation rules, and recovery behavior. If the tree hides the difference between truth, derivation, cache, speculation, observation, and explanation, the code will eventually treat them as interchangeable. That is how stale state becomes authoritative by accident.

17. Write structures and read structures are distinct but paired. Write-side structures declare change; read-side structures declare consumption. Mutations, projections, queries, subscriptions, invalidation rules, and view models may share vocabulary, but they do not share authority. The tree must preserve their separation while making their contractual relationship discoverable. A generic `logic` folder destroys the difference between changing truth and observing truth.

18. Boundary crossings must be spatially locatable without grep. Every place a component touches the outside world — network, storage, queue, file system, scheduler, external service, generated SDK, hardware, operating system, or human approval path — must occupy a visible boundary location. External effects are too important to hide inside generic domain code. If finding external effects requires searching for client libraries, the tree is lying. Hidden boundary crossings create diagnostic blindness during incidents.

19. Dependency direction must encode direction of knowledge. Boundary adapters may know external formats and domain contracts; core domain code may know domain contracts and abstract ports; storage implementations may know persistence mechanics and storage contracts. More stable or higher-authority concepts must not depend on more volatile or lower-authority mechanics. When core meaning imports boundary detail, the dependency graph has inverted the domain.

20. A directory tree is only a claim; the import graph is the proof. Components must depend through public contracts, not deep internal topology. Visibility must shrink to the smallest valid scope. A clean folder layout with cross-cutting deep imports is decorative architecture. If a claimed boundary can be bypassed without friction, it is not a boundary; it is a suggestion. Decorative architecture is worse than no architecture because it creates false confidence.

21. A component’s public surface must be narrower and more stable than its internal topology. Internal folders may change as the domain becomes clearer; external consumers must depend on durable capabilities, not current submodule arrangement. Deep imports turn every internal refactor into a breaking change and remove the system’s freedom to improve its own structure. A public surface that mirrors internals is not encapsulation; it is exported topology.

22. Shared code must earn its shared location by proving shared authority, not shared convenience. Shared infrastructure is valid when multiple domains depend on the same concept for the same semantic reason. Similar shape is not enough. `common`, `helpers`, `utils`, and `shared` often mean responsibility was extracted by convenience instead of meaning. Similar code with different semantic authority may be safer duplicated than falsely unified. False unification creates shared failure where the domain did not require shared fate.

23. Test topology must falsify the production topology. If a production responsibility is real, its behavior, fixtures, fakes, assertions, and failure cases must be testable without constructing unrelated domains. When tests require a global `world`, generic `actions`, broad fixture piles, or cross-domain setup for local behavior, the production boundary is either too broad, too leaky, or incorrectly placed. That is test fog: the test can no longer show which responsibility failed.

24. Test support obeys the same ownership and visibility laws as production support. Fixtures, fakes, builders, scenario runners, assertion helpers, and deterministic test infrastructure must live at the narrowest scope that can use them. A helper that makes tests shorter but hides responsibility has harmed the structure. Test code should reduce ceremony without collapsing the domain model it is supposed to verify. Convenience in test support is dangerous when it makes unrelated responsibilities fail together.

25. Growth must make the system more explicit. A healthy structure absorbs new complexity by adding named responsibilities, not by enlarging vague containers. When growth repeatedly lands in the same generic folder or file, the structure is failing to expose the system’s fracture lines. Generic growth is how god files form without anyone explicitly choosing them. The codebase should become more navigable as it grows, not merely larger.

26. Deletion, replacement, ownership, and mocking are tests of structural truth. A coherent responsibility can be removed, replaced, mocked, versioned, delegated, deployed, scaled, or owned without combing through unrelated areas. If removing a capability means editing scattered fragments across the tree, the structure was organized around mechanics instead of ownership. Deletion resistance is evidence of false ownership. A folder that cannot be owned cannot be maintained.

27. Generated artifacts, compatibility bridges, legacy adapters, and temporary structures must be named by their constraint, not by convenience. `generated/openapi`, `compatibility/v1_to_v2_identity_bridge`, and `legacy_import` are bounded structures because they explain why they exist. `old`, `new`, `temporary`, `misc`, and `stuff` are entropy with names. A shortcut without a boundary becomes architecture; a temporary folder without an exit condition becomes permanent. An unnamed exception becomes precedent.

28. Structure is documentation only when it is enforced. The tree should answer what concepts exist, what they own, where authority lives, where truth lives, where boundaries are crossed, and how components may depend on one another. But a structure not backed by visibility, package exports, façade contracts, dependency rules, and test topology will drift into decoration. The tree is the promise; enforcement is the proof. Unenforced structure decays into folklore.

29. Navigability under pressure is the final test. A new contributor should locate the right concept without knowing the implementation. A senior engineer should predict dependency direction without reading imports. A test author should know where fixtures belong. An operator should know where boundary code, policy, persistence, and diagnostics live. The structure succeeds when pressure makes the system easier to navigate, not harder, and when the next correct edit is easier to locate than the next convenient edit.
