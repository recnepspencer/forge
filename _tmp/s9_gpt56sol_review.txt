## Findings

1. **Critical — The spec does not define a real model-to-implementation conformance mechanism.**  
   S.9 promises that code states map to checked model states, but the implementation mechanism is mostly “emit a typed trace, replay it through the model, compare verdicts” ([S.9:409](/C:/Users/Esther/Documents/Programming/forge_workspace/forge/_docs/forge-store/storage-foundation-s9.md:409)). That proves the trace adapter agrees with the model; it does not prove the runtime executed the modeled transition. A shared mapping bug, omitted event, or dishonest normalization can make both sides agree while production violates the protocol. This is especially weak because a modeled state may map merely to “a concrete runtime type **or typed trace row**” ([S.9:167](/C:/Users/Esther/Documents/Programming/forge_workspace/forge/_docs/forge-store/storage-foundation-s9.md:167)), while the roadmap requires matching code states and typed transitions ([roadmap:1014](/C:/Users/Esther/Documents/Programming/forge_workspace/forge/_docs/forge-store/forge_store_roadmap_2.md:1014)). The spec needs an explicit refinement/conformance contract: authoritative runtime transition types, sealed constructors, transition receipts emitted at the mutation boundary, an independently defined abstraction function, and completeness rules proving that relevant transitions cannot occur without an observable receipt.

2. **Critical — Six isolated models do not address the roadmap’s actual “crash plus concurrency” risk.**  
   The roadmap targets state machines most likely to fail under crash combined with concurrency ([roadmap:990](/C:/Users/Esther/Documents/Programming/forge_workspace/forge/_docs/forge-store/forge_store_roadmap_2.md:990)). The spec divides WAL, recovery, compaction, leases, repair, and import into separate protocol families, but never defines compositional models or cross-family invariants. The dangerous failures live between them: crash during compaction while a lease survives; checkpoint publication racing quarantine; repair racing reclaim; import admission followed by crash before root publication; WAL retention advancing while an old compaction generation remains reachable. “Shared evidence vocabulary” is not composition. At least one integration model must own shared frontiers—durability, visibility, reachability, quarantine, and admission—or the milestone will prove six clean local stories while the real combined protocol remains folklore.

3. **Critical — There is no formal-model contract, only model-shaped vocabulary.**  
   The spec never chooses a modeling language/tool, names model files, defines constants/configurations, states initial conditions, enumerates actions, states safety or liveness properties, declares fairness assumptions, or explains finite-state abstraction. “Checked model,” “legal terminal state,” and `states.rs/actions.rs/invariants.rs` are not enough. The directory skeleton contains no `.tla`, `.cfg`, PlusCal, Apalache, Alloy, or equivalent artifacts at all ([S.9:486](/C:/Users/Esther/Documents/Programming/forge_workspace/forge/_docs/forge-store/storage-foundation-s9.md:486)). It also does not distinguish exhaustive checking within declared bounds from proof over an unbounded protocol. This leaves room for formal-methods theater despite explicitly rejecting it.

4. **High — Phase 1 assigns global protocol-inventory authority to the wrong handoff.**  
   The spec makes `S8LayoutHazardInventory` and `StorageFoundationS9LayoutHandoff` publish the state machines and hazards for all S.9 work ([S.9:91](/C:/Users/Esther/Documents/Programming/forge_workspace/forge/_docs/forge-store/storage-foundation-s9.md:91)). But S.8 owns layout and access-path discipline, not WAL, recovery, buffer-pool leases, repair, quarantine, or import authority ([roadmap:925](/C:/Users/Esther/Documents/Programming/forge_workspace/forge/_docs/forge-store/forge_store_roadmap_2.md:925)). Worse, Phase 1’s subsystem list omits WAL, physical integrity, the offline verifier, and import/replication owners. S.8 should contribute a layout-hazard slice; each runtime protocol owner should publish its own typed inventory. S.9 should assemble those without allowing the layout crate to restate other crates’ authority.

5. **High — The spec violates two explicit roadmap-wide requirements: hardware assumptions and exact counters.**  
   Roadmap 2 requires every sequence to expose exact counters and name the backend/hardware assumptions supporting its claims ([roadmap:112](/C:/Users/Esther/Documents/Programming/forge_workspace/forge/_docs/forge-store/forge_store_roadmap_2.md:112)). S.9 provides neither. That is particularly dangerous for WAL/checkpoint modeling: `fsync`, durable rename, sector atomicity, torn writes, buffered versus direct I/O, and uncertain completion are backend capabilities, not universal atomic actions. Without a parameterized media contract, the model will likely encode an unrealistically clean storage device. Required counters should cover transition receipts, unmapped runtime edges, trace omissions, normalization rejections, explored states/transitions, invariant checks, deadlocks, truncated searches, and counterexample localization—not merely test pass/fail.

6. **High — Replication admission, explicitly required by the roadmap, disappears into import admission.**  
   The roadmap requires “replication/import admission where it depends on physical evidence” ([roadmap:998](/C:/Users/Esther/Documents/Programming/forge_workspace/forge/_docs/forge-store/forge_store_roadmap_2.md:998)). The spec names import admission, gives it an `import_trace.rs` and `import_admission/` model, and never defines a replication-admission family ([S.9:500](/C:/Users/Esther/Documents/Programming/forge_workspace/forge/_docs/forge-store/storage-foundation-s9.md:500)). Replication is not merely import under another label: it has peer progress, replay/duplication, partial transfer, divergence, resume, source epoch, manifest/chunk ordering, and potentially continuing concurrency. Either add a distinct replication-evidence admission model or precisely define the shared protocol and the parameters that preserve their different failure modes.

7. **High — The phase plan is mostly a list of categories, not a sequence of coherent transitions.**  
   Phases 3–7 are parallel protocol subjects. Phase 3 does not produce a typed artifact consumed by Phase 4; Phase 4 does not establish a proof needed by Phase 5. Phase 9 introduces the directory skeleton after the models, mappings, runner, and traces supposedly exist. That is backwards. The topology and dependency direction must be frozen before implementation. A true sequence would look more like: freeze owner-published protocol contracts → freeze formal semantics/toolchain and abstraction law → build one end-to-end reference protocol → close instrumentation/conformance → model remaining local protocols → model cross-protocol composition → mutation/certification closeout. Protocol families can be workstreams inside those phases, but they are not themselves sequential phases.

8. **High — The runtime/formal/certification ownership boundary is contradictory and invites dependency inversion.**  
   The new formal-model crate is called the “production-owned protocol vocabulary, runner, and mapping authority” ([S.9:174](/C:/Users/Esther/Documents/Programming/forge_workspace/forge/_docs/forge-store/storage-foundation-s9.md:174)), while runtime authority supposedly remains in runtime crates. The spec never states dependency direction. If runtime crates import formal-model trace types, the model layer becomes production protocol law and can introduce circular or downward dependencies. If the formal crate imports internal runtime types, it becomes coupled to private topology. Define a narrow runtime protocol-observation facade owned by each runtime crate; formal mappings consume those public transition records. Certification consumes formal verdicts. No runtime mutation path should depend on the model runner or certification.

9. **High — The protocol content is too clean and omits the ugly state transitions that formal modeling is supposed to expose.**  
   The phases offer narratives, not state/transition tables. Material omissions include:

   - WAL/checkpoint: submitted versus completed flush, ambiguous I/O completion, torn WAL frames, segment rollover, pageLSN comparison, replay idempotence, checkpoint begin/end, retention/truncation eligibility, failed directory sync, and acknowledgment loss after durability.
   - Recovery: candidate discovery, integrity/authenticity validation, precedence selection, redo, root publication, repeated restart, unsupported/unavailable key custody, and failure while publishing recovered state.
   - Compaction: competing compactors, durable manifest/root CAS, orphan products, partial index publication, cancellation, retry, rollback, tombstone/version retention, and ABA generation reuse.
   - Leases/reclaim: acquire-versus-epoch-advance race, expiry/revocation, leaked holders, process crash, generation wrap, partial reclaim, and reuse before durable frontier advancement.
   - Repair/quarantine: plan authorization, blast-radius admission, source provenance, partial repair crash, post-repair verification, quarantine release, rollback, and operator cancellation.
   - Import/replication: capability negotiation, streaming partial receipt, resume, duplicate admission, lineage fork, missing chunks, authenticity unavailable versus failed, cancellation cleanup, and crash before authority publication.

   Without explicit states, guards, denials, and terminal outcomes, implementers will reconstruct these transitions from database folklore.

10. **High — Trace production is treated as harmless diagnostics even though crash protocols make trace durability part of the proof.**  
    The spec says runtime emits typed rows at publication seams and before policy finalization ([S.9:221](/C:/Users/Esther/Documents/Programming/forge_workspace/forge/_docs/forge-store/storage-foundation-s9.md:221), [S.9:401](/C:/Users/Esther/Documents/Programming/forge_workspace/forge/_docs/forge-store/storage-foundation-s9.md:401)). It never says whether those rows are authoritative transition receipts, optional diagnostics, durable media, or reconstructed observations. In-memory traces vanish at exactly the crashes being modeled; separately persisted traces can perturb ordering or falsely appear more durable than the operation. The spec must define trace atomicity, loss semantics, sequence identity, crash recovery, and whether omission means “unobserved,” “illegal,” or “instrumentation failure.”

11. **Medium — The directory skeleton is concrete in quantity, not in responsibility.**  
    Generic repeated files such as `states.rs`, `actions.rs`, `invariants.rs`, and `mapping.rs` say little about actual ownership and will encourage category-shaped files. `mod.rs` is present everywhere despite the spec warning against `mod.rs` business logic. The skeleton also lacks model source/configuration, abstraction/refinement mapping, backend assumptions, generated artifacts, tool lock/version, and protocol-specific certification fixtures. API shape is similarly weak: module names are supplied, but no key enums, transition signatures, sealed constructors, verdict topology, or fields are defined.

12. **Medium — “Open questions: None” is not credible.**  
    Tool choice, checking semantics, abstraction soundness, fairness, state bounds, hardware capability parameters, trace durability, mutation strategy, dependency direction, replication treatment, and cross-protocol composition are all unresolved. Declaring every phase closed conceals decisions that materially change what can be claimed.

## Strong parts

- The spec correctly rejects detached proof artifacts and keeps certification from owning runtime authority.
- Recovery precedence preserving losing candidates and contradictions is exactly the right instinct.
- The distinction between residency and reclaim eligibility is sharp and operationally valuable.
- Degraded, quarantined, rebuildable, and unrecoverable states remain distinct.
- Per-family controlled-defect lanes and counterexample localization are stronger than static “the model checker passed” evidence.
- The spec recognizes that compaction publication, visibility, reader retention, and reclaim belong to one lifecycle.

## Most important spec edits

1. Define the formal contract: selected toolchain, checked artifacts, state variables, actions, invariants, liveness/fairness assumptions, finite abstractions, model configurations, and reproducible commands.
2. Replace trace-replay equivalence with an explicit runtime refinement architecture: sealed runtime transitions, canonical transition receipts, independent abstraction mapping, instrumentation-completeness proof, and precise crash/loss semantics.
3. Add cross-protocol models for the shared durability, visibility, reachability, quarantine, and admission frontiers.
4. Make each runtime owner publish its own protocol inventory; reduce S.8 to the layout/access contribution.
5. Add the missing replication-admission family, backend/hardware assumption matrix, and exact S.9 counters.
6. Rewrite the phases as a real dependency sequence and add explicit state/transition/denial tables for every protocol family before presenting the directory skeleton.
