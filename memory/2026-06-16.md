# 2026-06-16

- Worth UI M4 Phase 4B implemented prepared content-slot facts across the
  native validation app boundary. Worth UI now exposes a read-only
  `WorthUiContentSlotCatalog` derived from prepared layout topology plus the
  canonical artifact, and the validation app projects it into
  `ValidationPageContentPlan` with private construction. The Products sample
  intentionally declares content out of layout order while tests prove mounted
  order follows layout traversal. Compile-fail fixtures now block internal
  content lowerer imports, local slot maps, direct egui layout authority,
  preminted content plans, visual-only certification, and direct `forge_query`
  dependency.
- Phase 4B QA found and fixed two architectural weaknesses: the egui boundary
  guard tolerated non-renderer shell/page-host UI contact, and the content-slot
  catalog initially derived slot/surface assignments by zipping topology slots
  with canonical mounts. The shell now exposes no egui-facing methods, the
  renderer owns page-host rendering, the guard only allows renderer/app egui
  imports, and Worth UI builds content-slot assignments from file-authored
  content-slot lowering before verifying canonical mount order.
- Phase 4B qa-tests/code-quality pass found two weak compile-fail fixtures and
  one underpowered dependency guard. The egui fixture now calls the real
  `ValidationWorkspaceShell::restore_from_snapshot` API with raw egui rects and
  fails on the typed restore snapshot boundary. The content-certification
  fixture now passes a real prepared `ValidationPageContentPlan` to the runtime
  receipt gate and fails because only a harness receipt can certify runtime
  evidence. The Forge Query manifest guard now rejects direct, table-form,
  target-specific, and renamed `package = "forge-query"` dependency forms.
- Worth UI M4 Phase 4C.5 implemented runtime-owned theme capability reload
  admission. `WorthUiRuntimeHost` now owns the active `CapabilitySnapshot`,
  prepares typed `WorthUiCapabilityReloadRequest` values from source-authored
  theme-token deltas, activates valid candidates at the runtime boundary, and
  rebinds the native header from runtime evidence. The validation app no longer
  denies valid theme edits locally; tests now prove valid theme edits mutate the
  runtime snapshot and rebind the header, malformed edits preserve runtime/header
  truth, combined source+theme reloads keep both evidence entries visible, and
  compile-fail guards prevent app code from minting capability reload evidence
  or prepared reloads.
- Phase 4C.5 QA found and fixed two real gaps: prepared theme capability reloads
  were bound only to the runtime instance, so an older prepared candidate could
  overwrite a newer active snapshot, and theme-token replacement hid repeated
  linear lookup breadth behind edited-token evidence. Capability activation now
  rejects stale active snapshot drift, validation tests prove stale prepared
  reloads cannot overwrite newer theme truth, theme-token replacement builds one
  index instead of rescanning per token, and evidence separately reports edited
  token count versus full theme-family rebuild breadth.
- Phase 4C.5 qa-tests/code-quality QA tightened the proof and API shape. Theme
  capability reload tests moved out of the broad reload-loop file and now
  pressure activation, malformed input, unknown tokens, duplicate tokens,
  multi-token cost evidence, and stale prepared replay. The capability reload
  request changed from a one-field theme struct to an enum-dispatched request
  so future action/state reload families do not turn the API into a bag of
  fields. Focused tests, validation-app tests, worth-ui lib tests, and the
  runtime authority compile-fail suite passed; the CI line-cap shell helper was
  unavailable locally because bash is not on PATH, so touched files were checked
  with targeted line counts instead.
